### 1.2-001 — E20 does not catch a capability whose only watch rule has no thresholds. Riverside has **six** signal-mute capabilities; E20 reports five — SPEC

`E20`'s stated purpose (`spec.md:110-112`) is *"it can never raise a signal, so it is invisible
to responsiveness scoring."* Its implemented predicate is only *"appears in no watch rule"*
(`backend/app/casepack/validate.py:665-680`, `if capability.key in lens.watched: continue`).
A rule with `warn_above: null` **and** `critical_above: null` can never raise anything, so a
capability watched only by such a rule is equally invisible — and is not reported.

```
$ cd backend && python3 -c "
from app.casepack.loader import load_casepack
p=load_casepack('packs/riverside_grocery')
caps={c.key for c in p.capabilities}
watched={r.capability for r in p.watch_rules}
thresholded={r.capability for r in p.watch_rules if r.warn_above is not None or r.critical_above is not None}
print('E20 reports (no rule at all)          :', sorted(caps-watched), '->', len(caps-watched))
print('truly signal-mute (no usable threshold):', sorted(caps-thresholded), '->', len(caps-thresholded))
for r in p.watch_rules: print(f'  {r.key:18s} cap={r.capability:20s} warn={r.warn_above} crit={r.critical_above}')"

E20 reports (no rule at all)          : ['customer_insight', 'financial_reporting', 'marketing_sales', 'service', 'store_operations'] -> 5
truly signal-mute (no usable threshold): ['customer_insight', 'financial_reporting', 'firm_infrastructure', 'marketing_sales', 'service', 'store_operations'] -> 6
  ord_cap_01         cap=order_fulfilment     warn=0.8 crit=0.95
  wh_rollout_01      cap=order_fulfilment     warn=None crit=None
  sec_identity_01    cap=firm_infrastructure  warn=None crit=None
```

The build implements the spec's literal text correctly, so this is not a build defect. It is
the check set being narrower than its own rationale.

**Consequence for 1.3, which is the part that matters.** `CG-1`'s closure condition in
`findings/content-coverage-2026-07-27.md` is *"a watch rule for **every** capability —
validator E20 clean."* A 1.3 author can satisfy that literally by adding five rules shaped
like `sec_identity_01` — `warn_above: null, critical_above: null` — and E20 would go green
with **seven of seven** capabilities still unable to raise a signal. The gate would certify
the exact condition it exists to prevent.

**Not blocking for 1.2.** Blocking for CG-1's closure. CG-1 must be restated as *"every
capability has a watch rule carrying at least one threshold"*, and E20's predicate widened to
match, before 1.3 authors against it.

### 1.2-002 — §9.1's replacement acceptance gate predicts errors the check set provably cannot produce — SPEC

`spec.md:264-274` defines the amended gate as *"every error it reports is traceable to a
logged content gap"*, then lists what it expects to see:

```
  5 × E20   ...  have no watch rule                                    → CG-1
  n × …     thin event deck, 3 cards across 6 rounds × 4 strategies    → CG-2
  n × …     no obligation_rules.yaml, ethics layer inert               → CG-5
  n × …     round-3 capital authored in two places                     → CG-6
```

Three of those four lines are wrong about the build's output, and two are wrong *by
construction* — no check in §5.1, §5.2 or §5.3 can produce them:

| Predicted | Actual | Why |
|---|---|---|
| `5 × E20 → CG-1` | **5 × E20** ✅ | correct, exactly the five capabilities CG-1 names |
| `n × … → CG-2` | **1 × W05, a WARN** | CG-2 surfaces as a warning, so it never reaches "errors it reports" at all |
| `n × … → CG-5` | **nothing** | `obligation_rules.yaml` is not a section 1.1's schema defines, so no code covers its absence |
| `n × … → CG-6` | **nothing** | no check reads `initial_state`; see 1.2-014 |

```
$ ./backend/bin/validate_casepack backend/packs/riverside_grocery | tail -3
  16 errors · 3 warnings · exit 1
$ ./backend/bin/validate_casepack --json backend/packs/riverside_grocery \
    | python3 -c "import json,sys,collections; print(collections.Counter(f['code'] for f in json.load(sys.stdin)))"
Counter({'E07': 8, 'E20': 5, 'E21': 2, 'E02': 1, 'W02': 1, 'W04': 1, 'W05': 1})
```

`spec.md:277-278` does say *"a CG that the validator **fails to catch** is a finding against
this spec"* — so the spec anticipated the disposition. But it then wrote the uncatchable CGs
into the acceptance criterion as expected output. The v1.1 amendment exists (`spec.md:299`)
because the original DoD pair *"was jointly unsatisfiable — the exact failure `SPEC_PROTOCOL
§4.1` exists to prevent."* The replacement is unsatisfiable in a quieter way: it can be
satisfied only by reading its own escape clause. `SPEC_PROTOCOL §4` — *"if you cannot write
the check, the invariant is underspecified"* — applies to §9.1's four bullets as written.

This is the `GOVERNANCE §6.1` blind spot in its textbook form: the author who wrote the CG
list, the check set, and the acceptance criterion did not notice that the first and the second
do not intersect on three of four rows.

**Not blocking.** The correct disposition is the one §9.1 itself names — file it, do not fix
it. That is this finding.

### 1.2-003 — The v1.1 amendment's §7 note asserts a superset relation that does not hold, and the builder had to invent two emitted codes because of it — SPEC

`spec.md:209-210`:

> *"E01–E11 is a superset of the six regardless, so this packet implements the remainder
> itself; six is the expected number, not a shortfall."*

The six functions and their homes in E01–E11:

```
$ cd backend && python3 -c "from app.casepack.checks import run_all_checks; \
    from app.casepack.loader import load_casepack; \
    print(list(run_all_checks(load_casepack('packs/riverside_grocery'))))"
['I3', 'I4', 'I5', 'I6', 'I7', 'I8']

$ grep -n 'results\["I' backend/app/casepack/validate.py
462:    for key in results["I3"]:        -> make_finding("I3", ...)   <-- no E-code
467:    for entry in results["I4"]:      -> E01
481:    for entry in results["I5"]:      -> E03
485:    for entry in results["I6"]:      -> E05
499:    for entry in results["I7"]:      -> E04
511:    for _ in results["I8"]:          -> make_finding("I8", ...)   <-- no E-code
```

Four of six map. `I3` (snake_case machine keys) and `I8` (YAML round-trip) have **no** code in
E01–E11 or E20–E23. E01–E11 is therefore not a superset of the six, and the builder had to
emit two findings under the raw 1.1 invariant identifiers to avoid dropping them:

```
$ grep -n 'make_finding("I3"\|make_finding("I8"' backend/app/casepack/validate.py
464:            make_finding("I3", "labels.yaml", f"key.{key}", line=None, key=key)
512:        findings.append(make_finding("I8", "pack.yaml", "casepack"))
```

**The builder's handling was right and is not the defect.** `spec.md:91` opens §5.1 with
*"Inherited from 1.1 §6 (I3–I8), plus:"*, which correctly treats I3–I8 as **additional to**
E01–E11. §7's note contradicts §5.1 of the same document. The build followed §5.1. Emitting
`I3`/`I8` as codes is therefore **declared scope, not undeclared scope** — the spec names
them by reference — and I rule the two codes in scope and correctly implemented.

The finding is against §7's sentence, which is false and, had the builder believed it, would
have caused two inherited invariants to be silently dropped from the validator.

**Not blocking.** §7's note needs correcting, and the code list in §5.1 should name `I3` and
`I8` explicitly rather than by inheritance, so 1.3's authors and 5.6's UI know they exist.

### 1.2-005 — Under `--json`, directory mode drops pack attribution and reorders relative to the text renderer. §3.1's one-producer-two-renderers guarantee does not hold in the mode 5.6 consumes — BUILD

Single-pack mode is clean. I compared the human and JSON renderers finding-by-finding across
Riverside and all 20 fixture packs: identical set, identical order, every message present in
both.

```
OK  backend/packs/riverside_grocery                human=19 json=19 set=True order=True msgs_in_text=True
OK  backend/tests/fixtures/packs/broken_E01        human= 3 json= 3 set=True order=True msgs_in_text=True
OK  backend/tests/fixtures/packs/warn_heuristics   human= 6 json= 6 set=True order=True msgs_in_text=True
   ... 21 packs, no divergence
```

Directory mode (O2, `validate.py:1159-1179`) is a second, unshared path and it diverges twice:

```
$ ./backend/bin/validate_casepack --json backend/tests/fixtures/packs | python3 -c "
import json,sys; d=json.load(sys.stdin)
print('total:', len(d)); print('first 3:', [(f['code'],f['file'],f['field']) for f in d[:3]])"
total: 30
first 3: [('E10', 'pack.yaml', 'pack_key.harbour_vet_group'), ('E00', 'capabilities.yaml', 'capabilities'), ('E01', 'capabilities.yaml', 'appointment_booking.required_roles.sms_gateway')]

$ ./backend/bin/validate_casepack backend/tests/fixtures/packs 2>&1 | grep -n "pack_key"
305:  ERROR  pack.yaml  pack_key.harbour_vet_group
```

1. **Order differs.** The shared `pack_key` finding is first in JSON and last in text.
   The flat JSON list is also not severity-sorted, while every single-pack block is
   (`validate.py:1015`).
2. **Pack attribution is lost.** The text renderer prints the pack directory before each block

`spec.md:70-71` promises *"one producer, two renderers, so **I5** cannot drift from the human
output."* In directory mode there are effectively two producers, and the machine-readable one
is the lossy one.

**Not blocking.** 5.6 has not been built and single-pack mode is the primary path. It must be
fixed before 5.6 consumes it.

### 1.2-006 — O2's cross-pack collision reuses E10's wording and gives an instruction that is wrong for the condition — BUILD

`validate.py:1121-1132` reports a duplicate `pack_key` across a directory of packs by
constructing an `E10`. `E10`'s message and fix (`validate_messages.yaml:104-107`) are written
for a duplicate key *within one collection in one file*:

```
$ ./backend/bin/validate_casepack backend/tests/fixtures/packs 2>&1 | tail -3
  ERROR  pack.yaml  pack_key.harbour_vet_group
         'harbour_vet_group' is declared 17 times, so only the last one would ever be used.
         Fix: give every entry in pack.yaml its own key, or delete the repeat.
```

The condition is seventeen *separate* `pack.yaml` files in seventeen *separate* directories.
The message says "declared 17 times... only the last one would ever be used", which is not what
happens — each pack loads fine; they simply collide on identity. The fix says *"give every
entry in pack.yaml its own key, or delete the repeat"*, which is not an action available to
the reader: there is no "pack.yaml" with seventeen entries, and no path is printed to say
which files are involved. An instructor following it exactly cannot make progress.

`dod.md:411-416` records the E10-reuse decision, so the reuse itself was declared. What was
not noticed is that reusing the *code* meant reusing the *wording*, and `spec.md:53`
(settled decision 3) requires *"Every check names its fix. A message that states a problem
without a next action is incomplete."* This one states a next action that does not exist.

**Not blocking** — O2 is not on any shipped path yet. Needs either its own code and message,
or an E10 message parameterised on which of the two conditions raised it.

'Customer Service' needs customer data at individual level, but no catalog item can hold
