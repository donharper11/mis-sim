`component_strategy_fit → strategies.yaml weights — **normalised** | transform`, and §3
decision 4 repeats it. §3 decision 6 and §5.2 point the other way. **That is a spec-internal
contradiction**, and `GOVERNANCE §7` is unambiguous: *"Spec vs README vs code disagreement →
stop, surface with evidence, await direction. Do not reconcile. Do not pick the one that seems
right. The disagreement is itself the finding."* `QUALITY_PROTOCOL §6` says the same. The

the table can be re-derived without touching mis_lite) — but it reconciled rather than
escalating, and it did so on the packet's largest content decision.

**Ruling: the outcome is correct and I would not have it changed. The route to it skipped a
gate.** This is not the conversion warning being set aside — the conversion ran, its output is
published in two places and the raw means ride in the pack — it is a spec conflict resolved
without an author. Half the finding is therefore against the SPEC for containing the
contradiction and giving §5.1's transform map no reconciliation rule against decision 6.

### 1.3-005 — CG-3's resolution holds for only 28% of the placement ladder: 54 of 75 options carry `lead_time_rounds: 0`, so no in-flight window exists and *abandoned mid-flight* is undetectable for them — BUILD · 1.6 (spec) · not blocking

CG-3 asked that duration be resolved *"authored catalog field or runtime state, **stated either
way**"*, because `1.4 §5.3`'s `follow_through = 1 − (abandoned + deployed-but-never-trained) ÷
initiated` cannot detect *abandoned* without knowing a project was still in flight.
`PROVENANCE.md §9` resolves it as `deployment_modes[].lead_time_rounds` (authored) plus 1.6's
`in_flight` (runtime). Both halves have a problem.

```
lead_time_rounds histogram over all catalog + platform placement options:
  {0: 54, 1: 17, 2: 4}      total = 75      zero-lead-time = 54 (72%)
```

A placement with `lead_time_rounds: 0` arrives in the round it is bought. It never enters an
in-flight state, so it can never be abandoned mid-flight — the term is undefined for it by
construction. That includes every `saas` mode in the pack, every `cloud` mode except four, and
eight `on_prem` modes (`pos_system_2011`, `accounting_package`, `store_spreadsheets`,
`next_gen_firewall`, `store_back_office_pc`, `backup_recovery`, `intrusion_detection`,
`integration_api`).

The runtime half is weaker still: `PROVENANCE.md:288` cites *"1.6 spec **open decision O2**"*.
An Open decision is by definition not settled (`GOVERNANCE §4.4`), and 1.6 is not built. So
CG-3's second half rests on a question another packet has not answered.

**This is "stated either way", which is what the gap literally required, and it is honest about
where each half lives.** It is not a resolution that lets `follow_through` be computed today.
The `deployed-but-never-trained` term *is* computable now (`training_options` coverage 0 past
arrival), so `follow_through` will not be zero — it will be silently incomplete, which is the
harder failure to see.

**Closes when** 1.6 settles O2 and either every placement carries a non-zero in-flight window or
`follow_through`'s `abandoned` term is redefined for instant arrivals.

### 1.3-006 — `I1`'s pasted evidence does not reproduce: the grep returns a hit and exits 0, on a file this packet added — BUILD · SPEC · not blocking

`dod.md:106` records I1 **PASS** with *"`grep -rniE "INSERT|UPDATE|DELETE|ALTER|DROP"
backend/scripts/harvest*` → zero hits, exit 1."* Run on the shipped tree:

```
$ grep -rniE "INSERT|UPDATE|DELETE|ALTER|DROP" backend/scripts/harvest*
backend/scripts/harvest_readback.py:22:sys.path.insert(0, str(Path(__file__).resolve().parents[1]))
$ echo $?
0
```

One hit, exit 0. `harvest_readback.py` was created by this packet, and the `-i` flag makes
`sys.path.insert` match `INSERT`.

**The invariant holds in substance and I verified that by reading, not by grepping**, as Part A2
required. `harvest_mis_lite.py` issues exactly two statement forms — an
`information_schema.columns` query (`:102-106`) and
`select coalesce(json_agg(t), '[]'::json) from (select … from <table>) t` (`:122-125`) — and
opens every connection with `PGOPTIONS=-c default_transaction_read_only=on` (`:88`), so the
server would refuse a write. `harvest_readback.py` opens no connection at all. **No writing
statement exists in either file.**

Two things are wrong anyway. First, a DoD row is marked PASS with output that was not produced
on the tree being shipped — `QUALITY_PROTOCOL §1`, *"an action is not done because the command
exited 0; verify the resulting state"*, and `SPEC_PROTOCOL §2.1`. Second, **the invariant's
check is a bad grep** — a case-insensitive substring match over an unanchored file glob, which
cannot distinguish a SQL verb from `list.insert`, `dict.update` or `str.replace`. That is the
**fifth** pre-flight-or-invariant grep on this project whose pattern could not return the right
answer (1.2 rows 3 and 4, 1.5 row 5, 1.3 row 1a, now I1), and the first that produced a *false
alarm* rather than a false pass. It is against the SPEC.

There is a smaller edge worth naming: `harvest_mis_lite.py:8-12` states that the forbidden verbs
*"are not spelled out here either"* precisely so the grep stays clean. Writing the artifact to
satisfy the examiner's text-match is not a defect when the artifact is genuinely compliant — and
it is — but it is the reason the invariant proves nothing on its own, and the sibling file the
same builder wrote is what exposed that.

labels.yaml:84  event_pos_support_ending       "Support for your point-of-sale version ends in

engine can supply them.
