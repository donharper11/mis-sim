**A5/A6 reading, recorded because the check is ambiguous.** "Disjoint" holds at the *role*
level: no accent role is reused as a status role or a chart role. It does **not** hold at
the value level — `--accent-1`, `--chart-1` and `--status-info-marker` all resolve to
`--blue-500`. That is the design, not a defect: spec §5.1 says primitives "may repeat
values freely" and that the point of two tiers is that roles "stay distinct and separately
changeable, and only the primitive is shared." I read A5/A6 as name-disjointness and they
pass. **Amend the checklist wording before 0.4b** so the next auditor does not read it the
other way and file a false finding.

**Value preservation — checked although the spec never asked for it.** For all 89 rows I
resolved the old token's literal value and the replacement's literal value and compared.
88 of 89 preserve their value exactly. The primitive set is also value-identical to the old
file: 38 distinct literals in, 38 primitives out, **no value present in the old file is
missing from the new one and no new value was introduced.** The one exception is 0.4a-002.

**Two traps the builder did not fall into**, worth recording because both were easy to miss:
`--color-surface-900` (`#0F1724`, navy) was correctly demoted to `--navy-900` and not
merged with `--text-primary` (`#0F172A`, slate — one character apart); and
`--color-text-secondary` (`#64748B`) was correctly mapped to `--text-muted`, not to the
similarly-named `--text-secondary` (`#334155`).

## Blocking

### 0.4a-001 — The rewrite orphans every token consumer in `frontend/src`, and the only screen in the app now renders wrong

`theme.css` was rewritten; the two files that read it were not, because spec §1 forbids
touching them. The result is live on the branch.

**8 of the 11 tokens `main.jsx` reads no longer exist.** `frontend/src/main.jsx:17-27`
builds the antd theme from `getComputedStyle(document.documentElement).getPropertyValue()`,
which returns `""` for an undeclared custom property. Resolved in a real browser against
this branch's `theme.css`:

```
EMPTY     --accent-navy            ""        EMPTY     --accent-red         ""
EMPTY     --color-primary-hover    ""        resolves  --text-primary       "#0F172A"
EMPTY     --accent-blue            ""        resolves  --text-secondary     "#334155"
EMPTY     --accent-green           ""        EMPTY     --bg-content         ""
EMPTY     --accent-amber           ""        EMPTY     --bg-card            ""
                                             resolves  --font-body          "'IBM Plex Sans', …"
```

**The visible consequence, in the browser, on this commit.** `npx vite --port 5199`,
`http://localhost:5199/_dev/tokens`, viewport 1280:

```
antd primary button   background: rgb(0, 0, 0)     — was #1E40AF (BECSR navy)
antd table header     black, header text near-illegible against it
swatch cards          89 rendered · 66 resolve to an empty value
console errors        none
failed requests       none
```

Evidence: `screenshots/0.4a/audit-devtokens-after-1280.png` (untracked — see 0.4a-004)
against the 0.2 baseline `screenshots/0.2/tokens-1280.png`. Compare the button and the
table header directly.

`frontend/src/pages/DevTokens.jsx:6-94` enumerates all 89 old names as string literals;
the 66 blanks are the 66 whose names the rewrite retired. The 23 that still render are
exactly the retained role names (5 text, 2 status-danger, 6 chart, 2 font, 8 space).

**Root cause is the spec, not the builder's judgement.** §5.1 mandates deleting these
names; §1 out-of-scope forbids editing "anything under `frontend/src/` except
`styles/theme.css`". Those cannot both hold. Phase 1 is not completable as specified.

**What the builder owed here.** `GOVERNANCE.md §4.4` and §7 required a stop-and-report on
exactly this conflict, and §1 of the spec even provides the lesser route ("File it; do not
repair it"). Neither happened: the session report describes "Frontend sanity: npm ci &&
npm run lint && npm run build — PASS" and does not mention the orphaned consumers. See
0.4a-003 for why those three commands could not have caught it.

**Remediation is the author's call, not mine. Two routes, both checked:**

1. **Amend the spec to permit updating the two consumers** to role names. I verified in the
   browser that a role-based antd theme resolves to the *same* values the old one produced:
   `colorPrimary → --action-primary = #1E40AF` · `colorPrimaryHover → --action-primary-hover
   = #1E3A8A` · `colorInfo → --status-info-marker = #3B82F6` · `colorSuccess →
   --status-ok-marker = #22C55E` · `colorWarning → --status-warn-marker = #F59E0B` ·
   `colorError → --status-danger-marker = #EF4444` · `colorText → --text-primary = #0F172A`
   · `colorTextSecondary → --text-secondary = #334155` · `colorBgLayout → --surface-page =
   #F1F5F9` · `colorBgContainer → --surface-card = #FFFFFF` · `fontFamily → --font-body`.
   All eleven resolve; none changes value. `DevTokens.jsx` would list the 113 declared
   tokens in two labelled groups — I confirmed **all 113 resolve, unresolved: NONE** — which
   also makes that page a working proof of the tier rule rather than a flat swatch dump.
2. **A back-compatibility alias block in `theme.css`.** Do not take this route. It
   reintroduces multiple names per value, which is the whole of finding 0.2-003.

## Functional

### 0.4a-002 — `--color-neutral` changed value under a row labelled "status rename"

```
old   --color-neutral: var(--text-muted)          → #64748B   (slate-500)
new   --status-neutral-marker: var(--slate-400)   → #94A3B8   (slate-400)
```

The other four rows in that group preserve their values exactly (`--color-positive`,
`--negative`, `--warning`, `--info` → the ok / danger / warn / info markers, all at the
`-500` weight). Neutral is the only one that moved, and the note reads "status rename",
which asserts no change.

It is also internally inconsistent with the scale the builder built: every other status
marker is a `-500` primitive; neutral alone is `-400`. Whichever way it is resolved —
repoint the marker to `--slate-500`, or keep `--slate-400` and change the note to record
the deliberate shift — the deprecation table must not claim a rename when the value moved.

This is the same failure class as 0.2-002: mechanical re-pointing across two token systems
without a semantic-relationship pass.

## Report

### 0.4a-003 — "npm ci && lint && build PASS" is a proxy signal for a claim it cannot support

`QUALITY_PROTOCOL.md §1` names this error class explicitly and cites the four false
"pushed" claims of 2026-07-26: *"an action is not done because the command exited 0. Verify
the resulting state, not the exit code."* All three commands pass on this branch — I re-ran
them — and all three are blind to 0.4a-001, because a missing CSS custom property is not a
syntax error, not a lint error, and not a build error. It resolves to `""` at runtime and
antd renders black. Zero console errors, zero failed requests. Only opening the page could
have caught it, and `GOVERNANCE.md §4.2` requires exactly that.

Push claim itself verified true: `git ls-remote` → `76d5e3ac…`, identical to local.

### 0.4a-004 — 0.4a screenshots cannot be committed; `.gitignore` blocks them and `.gitignore` is out of scope

```
$ git check-ignore -v screenshots/0.4a/situation-1440.png
.gitignore:16:screenshots/**/*.png	screenshots/0.4a/situation-1440.png
```

0.2 needed an explicit `!screenshots/0.2/*.png` negation (`.gitignore:17`). 0.4a has none,
so the nine screenshots the DoD requires will be silently ignored by `git add`. Adding the
negation touches `.gitignore`, which the DoD's own "no files touched outside" row does not
permit — and that row's permitted list (`theme.css`, `mockups/`, `CONTRACTS.md`, `dod.md`)
omits `screenshots/` altogether while another row in the same table demands nine files
there. `playthrough.md` F1 does allow `screenshots/0.4a/*`. Three documents, three
different answers.

This already bit this audit: my own evidence screenshot sits untracked at
`screenshots/0.4a/audit-devtokens-after-1280.png`. Resolve before Phase 2 or the visual
module ships with no visual evidence in the repository.

### 0.4a-005 — CONTRACTS.md entry omits the marker every other entry carries

The entry matches spec §5.2's text verbatim, so this is a spec-inherited nit rather than a
build error. But all eight existing entries are tagged **PROSPECTIVE**, the file states that
advance-declared contracts carry that tag and are converted "as code lands", and the header
`**Last updated:** 2026-07-26 (seeded at Phase 0, before implementation)` was not touched
even though this entry now has a real producer on disk. A7 asks for "the file's existing
format". Either tag it PROSPECTIVE (consumers do not exist yet) or bump the header to
record that one contract now has a live producer.

### 0.4a-006 — Part A cannot catch 0.4a-001; the checklist needs a consumer check before 0.4b

Every one of A1–A8 passes on a branch where the app renders wrong. The checklist verifies
the token file's internal structure and never asks whether anything that reads it still
works. Add a Part A row before 0.4b: *load the app in a browser and assert every token name
referenced anywhere in `frontend/src` resolves to a non-empty value.* Cheap, scriptable,
and it is the check that would have turned this pass green.

### 0.4a-007 — `design/06-plan-index.md` disclosed as untracked, now absent

The builder correctly reported it as outside the touch list and left it uncommitted — good
behaviour, and it is properly absent from the diff. It is now also absent from the working
tree (`git status --porcelain` clean, `ls design/` shows 01–05 only). Whatever it was, it
needs a disposition rather than a silent disappearance.
