## Data

### 1.1-002 — Round 3 has two authored values for capital remaining, and the pack is now the second home for the 0.4 contradiction

```
backend/packs/riverside_grocery/pack.yaml
  :14   budget.capex_per_round: [400000, 260000, 220000, 220000, 200000, 200000]
  :22   initial_state.budget.capital_remaining:   44000     (round 3, available 220000)
  :84   initial_state.review.capital_remaining:   46000     (round 3, available 220000)
  :82   initial_state.review.capital_committed:  174000
```

Same round, same `capital_available`, two different remainders. `:84` is derived —
220,000 − 174,000 = 46,000 exactly — while `:22` is separately authored. And the direction is
impossible: remaining *rises* from 44,000 to 46,000 after committing 174,000.

`SPEC_PROTOCOL.md §3` is the cleanest statement of the defect: *"One source of truth per fact.
Never introduce a second home for the same state without a reconciliation rule — and prefer
elimination over reconciliation."* Round-3 capital remaining now has two homes and no rule.
Either derive `:22` from committed spend, or drop `:84` and derive it at read time.

**This is finding 0.4-002 propagating.** I filed it against `review.html` on 2026-07-27 and
noted that a pass over §5.4 would stop the next module inheriting it. It was not made, and the
figures are now in the engine content — so fixing the mockups alone would no longer fix it.
The pack is the right place to fix it once.

## Report

### 1.1-003 — Withdrawing my own finding 0.4-003. It was a misreading

`pack.yaml:14` settles it: `capex_per_round: [400000, 260000, 220000, …]`. The budget is a
**per-round allowance**, not one programme total. So `$400,000 of $400,000` on a round-1
screen and `$44,000 of $220,000` on a round-3 screen are both correct, and 0.4's
`CAPITAL THIS ROUND` label — which the author introduced in `267907f` — says exactly that.

I filed 0.4-003 on the assumption of a single programme total, restated it across three audits
(as 0.3-018, then 0.3-018 again, then 0.4-003), and pressed for a §5.4 pass partly on its
strength. **That part was wrong and I withdraw it.** 0.4-002 is unaffected and stands, now as
1.1-002 above: it is a two-values-for-one-fact defect, not a per-round-budget
misunderstanding.

Worth noting how the error survived three passes: each time I checked the figure against the
*other screens* rather than against the model that produces it. The pack existed on `main`
before my 0.4 audit and would have answered it in one grep — which is a second, quieter cost
of 1.1-001.

### Disposition of 1.1-002 — no rework, carried forward *(added 2026-07-27)*

The rework packet originally gated a builder on an author decision here. **That gate is
withdrawn.** A builder reached it, correctly declined to choose a value, and reported.

The gate was wrong because it treated these figures as engine ground truth. They are not, yet:
`seed.py` persists nothing, `alembic/versions/20260726_0001_baseline.py` still has
`upgrade(): pass`, and neither 1.4 nor 1.6 exists. `initial_state` is authored display fixture
pinned to the 0.4 mockups — real content under `fc08c08`'s *"seed data, never stubs"*, but
consumed by nothing and **regenerated wholesale by 1.3's harvest.**

So the finding stands as a Data defect and the *timing* was wrong. Carried to
`handoffs/1.3-harvest/spec.md` §5.1a as **CG-6**, with the required output stated: derive both
roll-ups from `available − committed` rather than authoring them twice, which resolves round 3
to `46000` and makes the drift structurally impossible. 1.3 §5.4a already reads the pinned
figures back against 0.4 §5.4, which is the check that gives CG-6 teeth. Closing CG-6 closes
`0.4-002` as well.

**Auditor note.** Severity and gating are separate decisions, and this audit conflated them: a
**Data** finding was handed a fail-closed gate sized for a Blocking one. The cost was one
wasted builder cycle. The builder's stop was correct in both directions — it honoured the
instruction, and the instruction was what needed changing.

**On the module itself:** this is the strongest artifact the project has produced. Every
`CONTRACTS.md` entry that 1.1 was supposed to honour is honoured, including the subtle ones —
ordinal level-of-detail rather than string equality, bare role keys rather than display names,
normalised weights rather than mis_lite's un-normalised multipliers. The checks module is
genuinely executable, which is why re-running it took seconds. The one substantive defect is
inherited from a spec figure, not invented here.

**Before 1.2:** 1.1-001 needs a decision, because 1.2 is the validator and it will be built
against whatever `main` says the schema is. If engine code keeps landing on `main` inside spec
commits, the validator gets built against an unaudited target and the Phase 1 gate loses its
meaning.
