## Functional

- **1.6-A-001: `_missed_signals` collapses a signal's episodes by key, so it misreports the
  debrief's "you were told in round N".** `runner.py:247` builds
  `projected = {p.key: p for p in project_signal_state(ledger)}`, but `project_signal_state`
  returns **one row per episode**; keying by `s.key` keeps only the **last** episode's
  `acted_before_fire` and applies it to *every* episode of that key (loop `runner.py:249-255`).
  Proof (reproduced this session): a ledger with `ep1` fired-uncredited (a genuine miss) + `ep2`
  cleared-before-fire of the same key ⇒ `_missed_signals` returns `[]`, **dropping the real ep1
  miss** (the per-row projection correctly marks ep1 `acted_before_fire=False`). The reverse
  (last episode uncredited) over-reports earlier credited episodes — visible in the `--full` R3
  output where `wh_rollout_01` appears twice. Not on the scoring path (the scorer reads
  `project_signal_state` per-row directly, so the pin is unaffected), but `missed_signals` is a
  teaching-facing field (§5.3) and can silently omit a signal the student was warned about. Fix:
  zip ledger rows with their positional projection rows rather than a key-keyed dict.
  *Closing check:* the two-episode repro above returns the ep1 miss.

- **1.6-A-002 (= builder observation 3): the decision sheet is not applied to evolve the estate;
  each round's estate is authored seed data.** `runner.advance` implements step 1 (validate),
  step 3 (in-flight materialisation), step 4/7 (opex recompute), and the ActionRecord derivation +
  capex deduction — but **§5.2 steps 2, 4, 5, 6 estate mutations (retirements/cancellations, new
  purchases → nodes, org decisions → trained_count/adoption, governance → owner/sponsor) are NOT
  applied**; the post-decision estate is pre-seeded per round (`runner.py:285-287` comment; seed in
  `seeds/riverside_full.py:_seed_round_estate`). Spec §1 lists "applying a locked decision sheet to
  that state" **in scope**, and build step 2 / the DoD "resolution order matches §5.2 exactly"
  imply full delivery — so the delivered scope is narrower than the spec's headline. **However**,
  the `decision_line → estate-delta` input contract (how `category`/`capex`/`target_key` becomes an
  `arch_node`'s availability/throughput/placement/service_life, or updates `deployment_org_state`)
  is **genuinely undefined**: CONTRACTS.md has no purchase→node mapping; `design/02`/`design/05`
  describe it only via the future S3 purchase wizard. Per `GOVERNANCE §7` / `SPEC_PROTOCOL §8` an
  undefined input contract is a **STOP to the authority, not the builder's to fill** — so seeding
  the outcome rather than improvising a decision-DSL is the correct conservative choice, not a
  silent dodge. **This is a scope reconciliation the authority must rule** (correct the spec's
  scope wording, or dispatch a follow-up packet that defines the contract). Filed Functional, not
  Blocking, because the runner's actual deliverables are complete and correct and the gap rests on
  a contract the builder was forbidden to invent. *Closing check:* the authority records a ruling
  on the decision→estate contract; if in scope for 1.6, a purchase line adds the corresponding
  `arch_node` without a pre-seeded row.

## Rulings on the three builder observations

**Observation 1 — step-11 `fired_signals` binding: CORRECT (not a defect).** The spec §5.2
pseudocode literally passes `fired_signals=frozenset(fired)` where `fired` is fired **event** keys,
but `ledger.advance_ledger` compares `fired_signals` against **watch-rule** keys
(`ledger.py:272` `fired = rule.key in fired_signals`). Passing event keys directly would never
match, so `fire_round` would never stamp — a latent scoring bug. The builder's `_fired_signal_keys`
(`runner.py:188-200`) maps each fired event to the `pc.signal` of its `signal_open` preconditions,
which are exactly the watch-rule keys (confirmed against `events.yaml`: `warehouse_rollout_gap` →
`signal_open: wh_rollout_01`; and `Precondition.signal` holds the rule key, per
`events.capability_sequence` and `ledger._candidate_costs`). This binds to the engine's frozen
signature and stamps `fire_round` on the right signals — verified end-to-end in `--full`
(`wh_rollout_01` fired, `ord_cap_01` cleared-before-fire un-fired). The literal pseudocode was
shorthand; the semantic intent (decision 11: "bind to the frozen signature") is met. The builder
correctly surfaced the discrepancy rather than silently applying the wrong literal.

**Observation 2 — R3 pin reproduction: HONEST and SOUND.** The pin is genuinely preserved:
(a) hermetic — `test_engine_scoring.py` untouched (engine not in diff) and green after `--full`;
(b) the projection seam — `test_i10_projection_seam_preserves_pin` proves
`project_signal_state(sig.signal_history()) == state.signals` and scoring with the projected signals
still yields `0.656778`/`0.249744`, so 1.6's persist→load→project mechanism does not corrupt the
pin; (c) `--full` reproduces the credited/un-credited **pattern** via real `advance_ledger` mechanics.
The builder's claim that the exact R3 pin value cannot be reproduced by a coherent six-round game on
this estate is true and disclosed (R3 realised `0.2038 ≠ 0.249744`), and the commit says "pattern",
not "byte-identical". This does not paper over a defect — I10 (a round-runner change must not move
the pin) is what matters and is satisfied. The only residue is the spec §5.5 wording (`1.6-A-007`),
which the authority should correct.

**Observation 3 — estate-delta scope: ACCEPTABLE WITH CAVEAT; route to the authority.** Authoring
each round's estate as seed data rather than mutating it from a decision-DSL is spec-faithful given
that the `decision_line → estate-delta` input contract is **genuinely undefined** (no CONTRACTS
entry; only the future S3 wizard in `design/`). `GOVERNANCE §7` forbids the builder from filling an
undefined input contract, so seeding the outcome is the correct conservative choice and **not** a
silent dodge — the build runs end-to-end and the ActionRecord/capex/in-flight portions of
"applying the sheet" *are* delivered. **But** it leaves 1.6's headline capability (decisions evolve
estate, §1/step 2) only partially delivered, and the spec's "resolution order matches §5.2 exactly"
overstates it. This is a scope reconciliation for the authority (`1.6-A-002`): either correct the
spec's scope, or dispatch a follow-up that defines the decision→estate contract. Not blocking,
because the gap is an undefined contract, not omitted well-defined functionality.
