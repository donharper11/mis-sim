## Functional

### 1.1-r2-001 — An empty or comment-only `obligation_rules.yaml` makes the whole pack unloadable, contradicting the loader's own stated contract — BUILD

`loader.py:53-58` returns the default **only when the file is absent**. When the file exists but
is empty, `_read_yaml` returns `{}` (`loader.py:39`, `yaml.safe_load(handle) or {}`), and `{}` is
not a list.

```
$ cp -r backend/packs/riverside_grocery <scratch>/p_empty
$ : > <scratch>/p_empty/obligation_rules.yaml          # 0 bytes
$ ./backend/bin/validate_casepack <scratch>/p_empty

  ERROR  E00  Unreadable pack                 obligation_rules.yaml
         This pack could not be read: obligation_rules.yaml: obligation_rules: Input should be a valid list
         Fix: restore or repair obligation_rules.yaml in the pack directory, then run the validator again.
         Field: casepack

  1 error · 0 warnings · exit 1

$ printf '# authored in the next pass\n' > <scratch>/p_empty/obligation_rules.yaml
   -> the same E00

$ rm <scratch>/p_empty/obligation_rules.yaml
$ ./backend/bin/validate_casepack --json <scratch>/p_empty | ... Counter
Counter({'E07': 8, 'E20': 6, 'E12': 2, 'E21': 2, 'E02': 1, 'E14': 1, 'W02': 1, 'W03': 1, 'W04': 1, 'W05': 1})
```

**Deleting the file loads clean; creating it empty destroys the pack.** That is the opposite of
what `loader.py:84-86` says it does — *"A pack without the file loads clean; the empty list is the
honest reading of 'no obligations authored'"* — and `touch obligation_rules.yaml` is step one of
closing `CG-5`, so 1.3 is the packet that will meet it.

No existing pack has the file, so this breaks nothing today and is **not blocking**. It is
Functional because it is a real defect in code this packet added, in the exact workflow the
section exists for.

**Closes when** `_optional` returns its default for an empty file as well as a missing one —
`return _read_yaml(path) or default`. One line.

### 1.1-r2-002 — `placement_count` is still unexpressible: 1.5 §5.2 requires a placement **and** an integer, and only the integer was added — BUILD · REWORK INSTRUCTION · 1.5

1.5 §5.2's table is the specified shape and it is unambiguous:

```
| `placement_count`      | a placement + an integer  | (X) neither field |
| `policy_contradiction` | two **policy** keys       | (X) no policy field |
```

`rework-2.md` §3.5 lists five fields — `node`, `entity`, `policy`, `round`, `count` — and `count`
is annotated `# placement_count`. The placement half was dropped, and because `EventPrecondition`
is a `StrictModel` (`models.py:16-17`, `extra="forbid"`) there is no way to author it anyway:

```
$ PYTHONPATH=. python3 -c "from app.casepack.models import EventPrecondition as P; \
    print(P.model_validate({'type':'placement_count','count':3,'placement':'cloud'}))"
REJECT: Extra inputs are not permitted            (models.py:344-362)
```

So **two of the six unexpressible precondition types remain unexpressible** after 3.5, not one.
The builder reported the `policy_contradiction` half as `R3` and did not report this one; its
§3.5 evidence block prints `{'type': 'placement_count', 'count': 3}` as a pass.
`docs/casepack-schema.md:336` propagates it — the precondition table gives `placement_count` the
`count` field and nothing else, so an instructor authoring from the document cannot say *which*
placement.

This is the failure class 1.5 §5.2 names explicitly — *"a spec that describes a check the schema
cannot express produces either a silent proxy or a stopped builder"* — and 1.5's pre-flight row 7
greps `node:|entity:|policy:|round:`, so it **passes**, and 1.5's builder would not discover it
until build step 3.

Not blocking this packet: §3.5 gates 1.5, not 1.3, and `rework-2.md` §3.5 declares 3.5 droppable
in full. But it is a gap in the delivered item, unreported, and it is against all three — the
build did not deliver it, the instruction's field list did not name it, and 1.5 §10 item 3
("*and an integer count for `placement_count`*") is where the placement first went missing.

**Closes when** an author rules on the field (`placement: Placement | None` is the obvious shape,
matching `CONTRACTS.md`'s three-value enum) and it lands with `R3`'s second policy key.

### On the packet

Two things deserve saying plainly.

The first is that the compatibility rule — *"a schema change that silently destroys the validator's
test suite is a worse defect than the gaps it closes"* — was the right thing for the instruction to
put first, and it was honoured **completely**. Twenty-five packs produce byte-identical validator
output, in both renderers, with identical exit codes. That is not a change that happened not to
break anything; it is a change built so that it could not.

The second is about what "unblocked" means. This packet was dispatched to lift a gate, and it lifts
the half of the gate it owns: there is now a legal way to author every shape 1.3 and 1.5 need. The
other half was never 1.1's — a schema addition the validator has not been taught to read changes
what a pack may *say*, not what the gate *reports*. `metric_kind` is the clearest case: 1.3 can now
declare `presence` and the validator will go on calling those rules broken. Nobody did anything
wrong to arrive there — the sequencing 1.1 → 1.2 rework → 1.3 was always the plan — but the specs
downstream read as though addition 1 alone clears eleven errors, and it clears none. Saying so is
the difference between a gate that is lifted and a gate that has been moved.
