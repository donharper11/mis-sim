## 3. Adversarial probes the supplied tests do not perform

The prompt asked for probes where the shipped tests could pass despite an incorrect
implementation. Two gaps in the supplied coverage motivated these.

### 3.1 Pipeline probe — E29 driven through `validate()`, not the pure helper

`check_event_preconditions.py` calls `checks.check_precondition_shape()` **directly**. The
only case that reaches `E29` through the real validator is the `broken_E29` fixture, which
covers the *unknown-type* branch alone. A wiring defect between the helper and
`check_precondition_shapes()` — an unregistered check, a wrong `model_fields_set` argument,
a swallowed return value — would leave every shipped test green.

I rebuilt a real pack on disk for each case and ran the shipped `bin/validate_casepack --json`:

| Probe | Cases | Result |
|---|---|---|
| P1 all eleven valid shapes emit no `E29` | 11 | **11 PASS** |
| P2 one required field removed, per type | 11 | **11 PASS** — each names the exact omitted field |
| P3 one foreign field added, per type | 11 | **11 PASS** — each names the exact foreign field |
| P4 bare `{type: placement_count}` (both required absent) | 1 | **PASS** — `"is missing count, placement"` |
| P5 explicit YAML `null` on a required field | 1 | **PASS** — `ratio: null` reads as missing, not as authored |
| P6 explicit YAML `null` on a foreign field | 1 | **PASS** — still reported as extra |

**33 shape cases + 7 edge cases, all correct.** This is the evidence on which the "exact
required and forbidden field shape" requirement is signed off — not the builder's helper-level

## 4. Findings

Severity order per `QUALITY_PROTOCOL §4`: Blocking → Functional → UX → Data → Report.
**No Blocking and no Functional findings.**

### UX

- **`1.5-RC-001` — `E29`'s message is ungrammatical and its `fix` names no remedy the author
  can act on.** The catalogue renders `message: "Has an invalid condition shape: it {problem}."`
  (`validate_messages.yaml:280`) against `problem = f"type '{condition.type}' is missing …"`
  (`validate.py:754`), producing:

  > `Has an invalid condition shape: it type 'staffing_over' is missing ratio.`

  "it type '…' is" does not parse as English, and it is the only message in the catalogue that
  does not. Its neighbours read cleanly — `E24`: *"Reads the policy switch 'x', which this
  company does not have."*; `E27`: *"Says it is cleared by 'x', which is not something a team
  can actually do."*

  Separately, the `fix` line lists the eleven **type names** but never the **fields the declared
  type requires** — which is the one thing an author facing "is missing ratio" or "also carries
  count" needs. `E26` and `E27` both name their exact valid set in the fix. 1.2 spec §3
  decision 3 requires every check to name its fix, and §2 requires validator output to read for
  instructors, not engineers; "invalid condition shape" is engineer vocabulary.
  *Suggested owner:* 1.2 next. Non-blocking: the diagnostic is correct and locates the defect
  precisely.

### Data

- **`1.5-RC-002` — the placement vocabulary now has a second home in `models.py`.**
  `models.py:20-23` already defines `class Placement(StrEnum)` with exactly `on_prem`, `cloud`,
  `saas`, and it is the type of two existing fields (`models.py:225` `deployment_modes`,
  `models.py:266` `placement_options`). The new field at `models.py:361` re-declares the same
  three values as a bare `Literal["on_prem","cloud","saas"]`.

  Behaviour is identical — I confirmed `placement: hybrid` is rejected — so this is not a defect
  in the build. It is flagged because `SPEC_PROTOCOL §3` forbids a second home for the same fact
  without a reconciliation rule, and `CONTRACTS.md` `placement` is explicit that these three
  values are canonical. The `Literal` form was **frozen verbatim by the readiness spec**
  (`readiness-spec.md:14-15`), so the builder implemented exactly what it was given; under
  `GOVERNANCE §7` the spec/codebase divergence was the thing to surface rather than resolve, and
  it was not surfaced. A future edit to `Placement` will now silently miss `EventPrecondition`.
  *Suggested owner:* 1.1 next (one-line change to `Placement | None`, or an explicit note in
  `CONTRACTS.md` that the two forms are deliberately parallel).

### Report

- **`1.5-RC-003` — two-thirds of `E29`'s specified behaviour has no fixture.** The `broken_E29`
  fixture is a one-line delta from `minimal_valid` (`{type: signal_open …}` → `{type:
  not_a_precondition …}`), so the matrix exercises the **unknown-type** branch only. The
  **missing-required** and **foreign-field** branches — 22 of the 33 behaviours the readiness
  spec froze, and the entire per-type contract — reach the validator through no fixture at all.
  `check_fixture_matrix.py`'s own header states the standard: *"a code with no fixture is
  untested"*; here the code has a fixture that covers one of its three branches.

  I established by probe (§3.1) that all 33 cases behave correctly **today**, so nothing is
  wrong in the shipped artifact. The finding is that the guard is thinner than the contract, and
  M2/M3 above show the matrix cannot see either branch break. Two more one-line fixture packs
  (`broken_E29_missing`, `broken_E29_foreign`) would close it.
  *Suggested owner:* 1.2 next.

- **`1.5-RC-004` — `pytest -q` is not the guard the DoD implies, and the two new focused checks
  are wired into nothing.** The DoD row *"Full backend suite · PASS · `pytest -q` → 35 passed"*
  is true but does not bear on this packet: pytest collects only `tests/test_*.py`
  (`--collect-only` returns zero hits for any `check_*.py`), and the repository has no CI
  workflow, `Makefile`, `pytest.ini`, or `pyproject.toml`. `check_event_preconditions.py` and
  `check_w08_rounds.py` are therefore the sole guard for five of the six defects in §3.2, and
  they run only when a human or agent remembers to invoke them by path.

  This follows the existing convention (`check_fixture_matrix.py`, `check_policy_options.py` are
  the same shape), so it is not a regression introduced here — but the packet adds two more
  unwired scripts to the pile, and the DoD presents an unrelated green suite as the evidence.
  *Suggested owner:* 1.2 next, or an explicit runner entry point.

- **`1.5-RC-005` — `git diff --check` is not clean over the mergeable range.**
  ```
  $ git diff --check cedd61f 1f060b4
  handoffs/1.5-event-signal-engine/readiness-spec.md:3: trailing whitespace.
  handoffs/1.5-event-signal-engine/readiness-spec.md:4: trailing whitespace.
  $ echo $?
  2
  ```
  Both are two-space Markdown hard line-breaks, introduced by the **author's** commit `1fe81c9`,
  not by the build: `git diff --check 1fe81c9 1f060b4` is clean, which is the scope the builder's
  DoD row reflects. Cosmetic and intentional as Markdown, but the DoD row reads as a
  whole-branch claim and the whole branch does not satisfy it. *Suggested owner:* author /
  trivial fix on merge.
