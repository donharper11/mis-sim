## Functional

### 0.3-021 — `components-detail` renders the spec's *descriptions of the tabs* as the tabs' content

Spec §5.4 describes what each tab holds. Three and a half of the five panels ship that
description as the visible text:

```
spec §5.4:257   Data         entities it owns, level of detail, who else needs them
rendered        Data         entities it owns · level of detail · who else needs them

spec §5.4:258   Connections  what feeds it, what it feeds, cost per connection
rendered        Connections  what feeds it · what it feeds · cost per connection

rendered        Overview     What it is, what it serves, who it is for, current status.
rendered        Lifecycle    installed round 2 · service life · vendor support horizon
                             ("installed round 2" is real; the rest are field names)
```

Only **Deployment** renders as actual content — "Runs on on-prem · config tier standard ·
capacity drawn 35%" — which shows the intended pattern and makes the others' emptiness
plain.

A mockup exists to show how a screen reads. This one shows a reader the *names of the fields
the screen will one day contain*, which answers none of "what does it cost, who does it
affect, what happens if it fails". It also puts **"level of detail"** on a student screen —
`CONTRACTS.md` § `entity.level_of_detail` says never to use that phrasing to students, and
gives the required register: *"you can see daily store totals — not individual baskets."*
I4's grep does not cover the phrase, so nothing caught it.

**Cause is shared.** §5.4 is a structural description, not the §5.7 verbatim copy block, and
it was read as copy. The fix needs §5.7 to carry real values for these five panels, then a
rebuild.

**This is also why B3 fails.** With the detail screen reading as a field list, and nothing on
the Components table signalling that a row opens it — no chevron, no link styling, no
affordance of any kind — a reader cannot discover where a system's settings live.

### 0.3-022 — Every panel renders at once, so "which step am I on" has no answer

Two instances, one cause:

- **`components-wizard`** shows the step-2 heading ("What are you adding?"), the step-3 tab
  highlighted, step 1's three deployment options, **and** the step 3 and step 4 panels —
  simultaneously. §5.3 is explicit: *"One step visible at a time, back permitted, cost
  running."*
- **`components-detail`** shows all five tab panels while the tab bar marks Overview active.

**This is what fails B9.** The purpose and unit panels list their options with **no selected
state**, while `Add to plan` sits live at the bottom. A reader concludes the steps are
optional. I11 — *"no skip/later affordance"* — passes literally, because there is no button
labelled "skip"; the requirement it was written to protect does not.

Spec §5.3 also says these steps are *"the pin… REQUIRED"*, and §5.3's own rationale is that
alignment is computable only because purpose and unit were declared. A mockup that reads as
though they are optional inverts the lesson.

## UX

### 0.3-023 — `[upgrade] [retire]` render as a single navy slab

`mockups/components-detail.html` — `.button` carries no display or width constraint, so two
consecutive `<div class="button">` stack full-width inside the Lifecycle card:

```css
.button { border:1px solid var(--action-primary); background:var(--action-primary);
          color:var(--action-primary-text); padding:…; font-weight:700; margin-right:… }
.badge  { display:inline-flex; width:fit-content; padding:…; border:…; }   ← same file
```

`.badge` already has the fix. `.button` needs `display:inline-flex; width:fit-content`. The
class survives elsewhere only because its parent happens to lay it out (`platform.html`'s
two-column action grid, `rollout-detail.html`'s single full-bleed action).

### 0.3-024 — `Close` renders as a large empty-looking box

`.tabs` is `display:flex; justify-content:space-between` with default `align-items:stretch`,
so `.close` — a bordered `div` — stretches to the container's full height and renders roughly
140×115 px containing one word. It reads as a layout fault, not a control.

### 0.3-025 — Nothing anywhere shows what is *selected*

Wizard deployment modes, purpose, unit, and every Rollout tier (`none $0` / `basic, 8 hours
$12,000` / `full, 24 hours $34,000`) render as flat bordered boxes. Nothing distinguishes
chosen from available, and nothing marks a required choice. This is the mechanism behind
B9's failure and it recurs on every screen that offers a choice. It also blocks the states
these screens exist to define — 0.5's component library needs a selected treatment to copy.

Related: the wizard's three deployment options each carry a `Partly done` badge. A status
badge on an unchosen *option* has no meaning; it reads as a rendering mistake.

### 0.3-026 — Large vertical dead space, worst on Platform

The Cloud panel holds one card against On-Premises' four, and the two-column grid equalises
heights: roughly **440 px of empty white** inside a bordered panel at 1440. `components` and
`rollout` show the same pattern between the filter bar and the table, and below the table.
Read cold, empty bordered regions look like content that failed to load.

### 0.3-027 — Platform's split-rule choices render as one run-on paragraph

*"What determines the split?"* is followed by all five options separated by `·` in a single
wrapped line. §5.7 lists them as five distinct choices; on screen they read as prose, and
nothing indicates a decision is being asked for.

The strategy chip reads *"Low-Cost Leadership · locked in round 2"* on a screen headed
**Round 1 of 6** — an event that has not happened yet, stated as fact. The chip is shell
chrome copied across all eight screens without adjusting for the one screen set in a
different round.

### 0.3-018 — carried forward, **not fixed**: the programme total still changes between screens

```
platform-empty.html   CAPITAL REMAINING   $400,000 of $400,000     (Round 1 of 6)
platform · components · rollout · …       $44,000 of $220,000      (Round 3 of 6)
```

Filed on 2026-07-26 against the v2 Situation states, still true in v3.1 with the two figures
now in separate files. The denominator is the total programme budget and cannot be both.
Both values are quoted from §5.4, so this remains the **author's** to resolve — but it now
reaches a reviewer as two screens that cannot describe the same company.
