## Findings

### Functional

**0.2-001 — `react-router-dom` ships a known high-severity advisory; a non-breaking fix
exists and was not applied.**

The DoD records "8 high vulnerabilities" as a single undifferentiated number. They are not
equivalent:

```
~6 of 8   brace-expansion → minimatch → eslint / eslint-plugin-react
          DEV-ONLY. Not shipped to the browser. Fix requires eslint@10 (breaking).
          Deferring is correct.

  2 of 8  react-router 7.12.0–8.2.0 → react-router-dom     GHSA-qwww-vcr4-c8h2
          RUNTIME DEPENDENCY. Shipped. `npm audit fix` is NON-BREAKING.
```

Real exploitability is low — the advisory is RSC-mode specific and this is a plain Vite
SPA — so this is not blocking. But a free fix on a shipped dependency should be taken
rather than logged. **Action:** `npm audit fix`, re-commit `package-lock.json`, and split
the two classes in the DoD note.

### UX / Design

**0.2-002 — `--color-primary-hover` is not a hue-consistent hover for `--color-primary`.**

Visible in `screenshots/0.2/tokens-1280.png`:

```
  --color-primary        #1E40AF   blue
  --color-primary-hover  #1E293B   slate   ← different hue family
```

globalstrat's original pairing was `#2563EB` → `#1D4ED8` — same hue, darker. The
re-point to BECSR values mapped `hover` onto `--bg-sidebar-active`, which is a surface
colour, not a darker primary. A button that shifts blue → slate on hover reads as broken.

**Action:** set `--color-primary-hover` to a darker shade of `#1E40AF` (e.g. `#1E3A8A`).
Mechanical re-pointing across two token systems needs a semantic-relationship pass, not
just a value swap.

### Design debt — input to module 0.6, not a 0.2 defect

**0.2-003 — 89 tokens with heavy aliasing and no usage guidance.**

Merging BECSR names with globalstrat names produced multiple names per value. `#1E40AF`
alone is reachable through **seven**: `--accent-navy`, `--text-link`, `--brand-primary`,
`--color-header-financial`, `--color-primary`, `--color-input-focus`, `--color-text-link`.
`--bg-sidebar` and `--color-surface-900` are both `#0F1724`.

The spec asked for exactly this merge, so the builder complied. But when 0.6 builds
`PanelCard` and `MetricCard`, nothing says which name to reference — and two components
picking different aliases for the same value is precisely the drift a design system exists
to prevent.

**Action for 0.6's spec (mine to write):** declare one canonical name per semantic role
and mark the rest as deprecated aliases, or collapse them. Do not leave the choice to
component authors.

### Report accuracy

**0.2-004 — the `typecheck` script does not type-check.**

`"typecheck": "vite build --mode typecheck"` on a project with zero TypeScript files is a
second build. The DoD's "npm run typecheck exited 0" is true but conveys nothing.
**Action:** remove the script, or rename it. Ladder rung 2's typecheck is legitimately
N/A for a JSX project — say that instead.

### Watch item — no action

**0.2-005 —** Slow-3G render of `/_dev/tokens` exceeded 60s (builder-reported). Acceptable
for an 89-swatch developer page that ships to no student. Noted only so it is not mistaken
for a baseline if a product screen later shows similar numbers.

## 0.2-001 — REMAINS OPEN. Builder's deviation is half correct.

Builder reported: *"no patched react-router-dom release is available in the registry."*

Verified against the registry — the forward paths are indeed blocked:

```
react-router-dom  latest = 7.18.1  →  react-router@7.18.1   IN vulnerable range
react-router      latest = 8.3.0   →  patched, BUT
                  peerDependencies: react >=19.2.7
                  We are pinned to React 18 (spec §3 decision 4, to match
                  globalstrat's components). v8 is foreclosed.
react-router-dom  not deprecated; no 8.x published
```

**But the downgrade path was not considered and it is open:**

```
react-router-dom@7.11.0  →  react-router@7.11.0
                            BELOW the vulnerable range (7.12.0 – 8.2.0)   ✅
```

Advisory range starts at 7.12.0. 7.11.0 is the last clean release in v7. Our entire
usage is three imports (`BrowserRouter`, `Routes`, `Route`) in `App.jsx` / `main.jsx`,
so the downgrade risk is negligible.

### Why take a downgrade over accepting the risk

Actual exploitability here is ~zero — the advisory is RSC-mode CSRF and this is a plain
Vite SPA with no server actions. On the CVE alone, accepting would be defensible.

The reason to fix it anyway is different: **a permanently-red `npm audit` trains everyone
to stop reading it.** This project runs for years across many modules. A clean audit
baseline is worth more than this specific advisory, because it makes the *next* finding
visible.

**Action:** pin `"react-router-dom": "7.11.0"` (exact, not caret — a caret re-enters the
vulnerable range). Re-run `npm ci`, confirm `npm audit --audit-level=high` reports only
the dev-only `brace-expansion → minimatch → eslint` chain. Re-run the playthrough:
routing is exercised by `/_dev/tokens` and `/nonsense`.

## 0.2-006 — NEW · constraint to carry forward

**React 18 forecloses the react-router v8 line** (peer `react >=19.2.7`). This will recur
for any dependency that has moved to React 19.

The React 18 pin exists only to match globalstrat's design-system components (spec §3
decision 4). **Revisit at module 0.6**: if those components turn out to work under React
19 — or if we rewrite rather than port them — the pin should be reconsidered, and
react-router 8 becomes available. Until then, treat React 19-only packages as unavailable
rather than discovering it per-package.

# Amendment 2 — 2026-07-26 · 0.2-001 CLOSED, reviewer error

**The builder stopped correctly and was right. The recommended downgrade was wrong.**

Advisory counts queried from npm's bulk endpoint (`registry.npmjs.org/-/npm/v1/security/
advisories/bulk`) rather than `npm audit`, which was returning 400 against the
regenerated tree:

```
  react-router@7.11.0    14 advisories  (6 high)   ← the recommendation
  react-router@7.12.0    13 advisories  (6 high)
  react-router@7.13.2    10 advisories  (5 high)
  react-router@7.15.1     5 advisories  (2 high)
  react-router@7.18.1      1 advisory   (1 high)   ← already installed
```

**Reviewer error:** I read one advisory's vulnerable range (`>=7.12.0 <8.3.0`) and
inferred that anything below it was clean. An advisory range describes *that advisory*,
not a version's total exposure. 7.18.1 is the cleanest release in the entire 7.x line;
the downgrade would have traded one low-exploitability advisory for fourteen including
XSS, SSR XSS, turbo-stream deserialization, and two DoS.

**Disposition:** stay on `react-router-dom@7.18.1`. Recorded as accepted risk **AR-001**
in `SECURITY.md`, with re-check tied to the module 0.6 React 18 revisit.

**0.2-001 — CLOSED**, no code change. The builder's original deviation was correct as
first reported.
